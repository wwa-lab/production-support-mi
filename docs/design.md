# 设计细节

状态：讨论稿，尚未批准实施，未导入真实资料。范围以 [README](../README.md) 为准，讨论结论及待决事项见 [决定记录](decisions.md)。

## 组织原则

对 INC / RCA，以“一个事故、一组来源、一份可核实的事实记录”为基础。邮件和 PPT 是证据载体，事故是事故知识组织与计数的基本单位；同一事故的邮件链、多版 RCA、PPT 和整改工单关联同一稳定事故 ID。RCA 修订保留版本与修订关系，不新增事故计数；无 RCA 的事故仍保留记录。

事故记录保留历史事实，跨事故页面引用这些记录，迁移适用性判断单独记录在 HCC 候选项中。支持以下追溯关系：

> 事故及 RCA／来源版本 → 故障机制／历史控制 → 目标设计中的对应位置 → 处理决定 → 验证场景与证据

一个事故可关联多个设计问题，一个设计问题也可由多个事故支撑。目标架构尚未确定时，先整理事故事实与来源，迁移关联保留“待评估”。

## 日常 FF log 与 SOP

按 D-09 的讨论方向扩展日常支持知识，保留现有“响应告警／消息／电话 → 处理 → 写 FF log → 发给值班同事”流程。告警、处理日志、问题与事故是不同对象；多条日志可关联同一问题，普通处理记录无需转成 INC 或 SOP。

- **复用日志**：使用 [FF log 模板](../templates/ff-log.md) 建立原记录索引。FFer 提供原记录位置即可开始整理；原文已有内容由整理人引用／提取，只针对影响理解或复用的缺口请记录者补充，不要求重写报告或填满所有字段。
- **保留依据**：沿用原 ID、位置、版本、记录者和访问范围。重发／转发不作为新问题；修订保留关系。补充与纠错注明提供人、日期和依据，处理成功不等于根因已确认。
- **形成 SOP**：整理人／Owner 先检索已有 SOP，基于可核实记录提出修订或使用 [SOP 模板](../templates/sop.md) 起草；保留来源，明确适用条件、步骤、结果检查、停止与恢复路径。普通日志可仅归档或关联已有知识。
- **复核与维护**：SOP 区分草稿、待验证／复核、已审核、待复核和已退役。验证与审核绑定 SOP、系统及环境版本，建议由另一位领域人员复核；旧日志中的一次成功不能直接成为通用操作依据。具体角色与发布规则仍待 D-07 / D-09 确认。
- **减少反馈负担**：使用结果继续写在原 FF log／工单，只增加 SOP ID、版本及实际偏差；SOP 页引用该反馈。实时处理状态留在既有工单中，迁移设计判断留在候选项中。

两个模板均为讨论稿，不代表已经建立导入或发布机制。日志格式和存储／发送渠道尚待确认，资料处理与存放需满足 D-06；日常日志与 SOP 的扩展试点尚未制定或执行。

## 现场排障助手：报错日志 → 历史 case → 补救建议

面向所有 FFer 增加问题处理中的使用入口：将本次完整报错日志或受控来源交给 agent，由 agent 基于可访问的 repo 知识快速定位历史 FF case、INC / RCA 和 SOP，提出本次优先采用的补救方案。此处的输入是系统产生的现场报错日志；FF log 是处理后编写并共享的处理记录，二者不能混为一类。

建议流程：

1. **理解现场**：从日志提取时间线、错误特征、组件及已发生的结果，定位到文件与行／事件位置。尽量复用现有告警和上下文，仅补问影响方案选择的信息，例如系统版本、当前业务影响、近期变更和已尝试操作。说明已读取的文件及时间范围，日志过长、缺段或未读完时不能声称已分析全部。
2. **检索与比较**：返回相关 case 和 SOP 的 ID、位置、版本与状态，说明相似点、关键差异和适用条件。相同错误码或症状只是线索，不等于根因相同；已退役或影响正确性而待复核的 SOP 不作为操作依据。
3. **形成建议**：先给出当前证据下的首选建议及理由，再列必要备选与切换条件。综合适用性、证据、业务影响、可恢复性和已有授权约束，不用检索相似度或未经校准的置信分数代替判断。“最佳”指当前已知条件下最合适的建议，不承诺唯一最优或必然恢复。
4. **按结果收敛**：建议先做能区分候选原因的只读检查；有适用依据和必要前提时，再列补救步骤。每步带预期结果、观察方法、停止条件和失败后的回退／升级路径。关键条件缺失、来源冲突或没有适用 case 时，明确暂不能给出可靠补救方案，提供最少必要检查与升级方向，不拼凑生产命令或参数。
5. **复用处理日志回流**：FFer 仍按既有流程决定并执行操作。实际采取的步骤、未采用建议、结果及偏差写入原 FF log／工单，必要时引用 agent 建议记录与知识版本，不另填报告。领域复核后再决定是否修订 case 或 SOP；agent 的回答不自动成为已确认知识。

建议回答结构：

| 内容 | 应说明什么 |
|---|---|
| 当前判断与首选建议 | 已观察事实、原因假设、推荐动作及尚未满足的条件分别标明 |
| 历史依据与差异 | case / SOP ID、位置、版本、状态，与本次环境或现象的匹配及不匹配点 |
| 先做的检查 | 检查什么、预期看到什么、结果如何影响下一步选择 |
| 补救步骤与验证 | 操作适用条件、预期结果、业务恢复判据；不能只检查告警消失 |
| 失败处理与备选 | 何时停止、如何恢复／回退或升级，以及改用备选的条件 |
| 未知项与覆盖范围 | 缺失信息、未读取日志、未确认结论及实际检索的知识版本／时间 |

这是建议生成能力的设计，不是自动修复授权。完整日志只可在 D-06 获准的环境与范围内处理，按要求处理敏感字段；临时分析不等于允许把日志或答案写入 repo。所有 FFer 可参与不扩大来源权限。日志和检索文本均作为待核实的数据，不得把其中夹带的指令当作 agent 操作授权。

后续扩展试点应覆盖已知 case、相似症状但原因不同、无匹配 case、SOP 过期、日志缺失和补救失败等情境，检查引用准确性、适用性判断、是否识别未知及停止条件；暂未执行，也不以历史检索命中视为补救有效。具体输入入口、接入工具、日志处理范围与验收条件仍待 D-06 / D-09 及扩展试点确认。

## 邮件与 PPT 的资料处理

1. 建立来源清单：分配 `source_id`，记录原始位置、资料类型、时间、版本、访问范围及内容指纹（可用时）。具体存储平台待定。
2. 邮件保留主题、时间、邮件链和附件关系；识别转发、引用正文及重复附件，防止重复计算。
3. PPT 检查正文、表格、图片中的文字、图表标注和备注。保存幻灯片序号；图表与 OCR 结果须与原页核对，不能把提取成功当成内容完整。
4. 优先通过原始 incident ID 关联；没有 ID 时，仅依据日期、系统、影响及描述提出关联候选，由人工确认。相似症状不等于同一事故或同一根因。
5. 同一事故可关联多份资料。区分事故发生时间、文档创建时间和修订时间；较晚邮件不自动覆盖已批准 RCA，冲突保留并交由负责人确认。
6. 确认后生成台账及 Wiki 页面。无法读取、定位或确认的内容进入缺失清单，保留处理状态。

## 台账建议字段

| 分组 | 字段 |
|---|---|
| 身份 | 内部唯一 ID、原系统 ID、关联来源 ID、归并依据 |
| 范围 | AMH/HASE、受影响服务／组件、严重级别及其原始定义 |
| 业务场景 | 业务流程、处理阶段、业务时间窗口 |
| 时间 | 发生、发现、恢复、关闭时间；原始时区；未知值 |
| 影响 | 业务影响描述及有证据的影响量，不能从叙述自行推算损失 |
| 原因 | 触发因素、已确认根因、促成因素、故障传播过程、原因标签及审核状态 |
| 历史依赖 | 当时相关组件、接口、数据状态、处理顺序及平台行为；仅记录有证据的内容 |
| 应对 | 临时恢复、长期修复、监控与预防控制、关联 Problem/Action、负责人和状态 |
| 有效性 | 整改是否验证有效、验证条件及证据；与工单关闭状态分开记录 |
| 证据 | 邮件标识／PPT 页码、原文片段、来源版本、审核人及更新时间 |

使用 [事故模板](../templates/incident.md) 保留业务场景和从触发、发现、影响扩散到恢复的时间线。每项关键事实附来源位置与版本；缺失不补齐，推断和冲突单列。工单关闭不能代替整改有效性证据。

## 统计口径

- 从事故清单统计事故数，不能只统计有 RCA 的资料；另报 RCA 覆盖率，定义分子和分母。
- 同时影响 AMH 与 HASE 的事故，在总体中按唯一 ID 计一次；各范围受影响次数不能直接相加为总体。
- 恢复时长与工单关闭时长分开。缺失时间不填零；指标展示有效样本数、缺失数及时间范围。
- 原因可多标签，标签次数之和可能超过事故数。根因未确认时保留未知。
- 版本化分类与计算口径；历史严重级别不可未经确认强制映射。跨年比较注明覆盖及口径变化。
- 重复事故须先定义“重复”的判定规则并经负责人确认；业务量变化时，不把次数变化直接解释为可靠性变化。
- 台账查询或脚本生成数字，LLM 解释时引用计算结果及关联事故；不从检索命中的几份文档估算全量。

## Wiki 结构与运行方式

INC / RCA 部分计划维护四类页面：单次事故、系统／组件、故障模式、HCC 改造主题；日常支持扩展增加 FF log 索引与 SOP，问题经验优先关联既有问题记录。各类页面引用对应稳定 ID 和来源版本，避免从多份二手摘要反复推导事实。

| 浏览入口 | 组织内容 |
|---|---|
| 业务流程视角 | 引用相关事故、业务阶段及迁移验证场景 |
| 系统／组件页面 | 引用涉及的事故、历史依赖及控制措施 |
| 故障模式页面 | 记录机制描述、适用条件、关联事故、归组依据及确认状态 |
| HCC 改造主题页面 | 汇总候选项及其关联的设计决定、验证场景和证据 |

这些入口引用同一份事故事实，不分别维护副本。年份、AMH/HASE、严重级别作为筛选维度，用于趋势分析。

故障模式的关联须记录支持及相反证据、来源版本和审核人。症状相似不代表机制相同；尚未确认的关联保留为候选，不计入已确认重复问题。重复统计口径仍待 D-04 确认。

- **Ingest**：识别新增／修订来源，提取并审核，更新相关页面及变更日志。
- **Query**：事实回到来源，数字回到台账计算；回答注明范围和资料截至时间，证据不足时说明未知。
- **Lint**：检查失效引用、孤立页、重复页面、冲突和来源更新。链接及结构可用规则检查，事实与因果仍需领域评审。
- **修订**：源资料修订后标记关联页面、SOP、迁移判断及验证场景待复核，保留旧版本及修订理由；目标设计或验证输入变化时重新评估原结论与证据的适用性。模型建议不直接变成已确认 RCA 或已审核 SOP。

原始来源保持只读；派生页面继承来源的访问限制。混合不同权限材料前必须确认可见范围；源材料撤回或权限变化时复核派生内容。使用哪个 AI 环境及是否存放内部材料，见 D-06。

## HCC 改造证据

使用 [候选项模板](../templates/modernisation-candidate.md) 记录历史事故、问题机制、控制缺口、目标设计变化和验证方式。系统负责人确认事实，HCC 架构负责人评审适用性与优先级。

历史 RCA 描述事故发生时的情况；迁移适用性判断引用 RCA，并绑定目标设计版本，不能写回为原 RCA 的结论。每项候选记录回答：

- 原故障条件在目标设计中是否仍存在？依据是什么？
- 原有控制由什么机制承接，需要保留、替换还是重新验证？
- 若认为不再适用，具体是哪项设计变化消除了发生条件？
- 尚缺哪些信息、由谁确认？未决项保留待评估状态。

候选项是建议；不能仅凭旧系统曾发生事故就认定迁移会消除问题。整改状态来自现有工单，保留查询时间，避免另建一套失真的行动清单。

## 迁移验证场景

在候选项模板中按场景逐项记录，使用稳定场景 ID，关联事故及 RCA／来源版本。每个场景包含业务前置条件、触发或故障注入方式、预期业务结果、观察方法及验收条件；由业务与架构负责人确认适用性和验收条件，不凭历史资料自行设定缺失阈值。

场景设计与执行结果分开。后续执行证据须记录环境、目标系统／构建及设计版本、实际结果、证据位置、执行时间和审核人。未执行保持“未执行”，设计已评审不等于验证通过；旧平台的整改验证也不能代替新平台的验证。

本节仅定义未来记录方式，不启动场景执行、故障注入或真实资料处理。
