# 设计细节

状态：提案。范围以 [README](../README.md) 为准，待决事项见 [决定记录](decisions.md)。

## 邮件与 PPT 的资料处理

1. 建立来源清单：分配 `source_id`，记录原始位置、资料类型、时间、版本、访问范围及内容指纹（可用时）。具体存储平台待定。
2. 邮件保留主题、时间、邮件链和附件关系；识别转发、引用正文及重复附件，防止重复计算。
3. PPT 检查正文、表格、图片中的文字、图表标注和备注。保存幻灯片序号；图表与 OCR 结果须与原页核对，不能把提取成功当成内容完整。
4. 优先通过原始 incident ID 关联；没有 ID 时，仅依据日期、系统、影响及描述提出关联候选，由人工确认。相似症状不等于同一事故或同一根因。
5. 同一事故可关联多份资料。区分事故发生时间、文档创建时间和修订时间；较晚邮件不自动覆盖已批准 RCA，冲突保留并交由负责人确认。
6. 确认后生成台账及 Wiki 页面。无法读取、定位或确认的内容进入缺失清单，保留处理状态。

## 台账建议字段

| 分组 | 字段 |
|---|---|
| 身份 | 内部唯一 ID、原系统 ID、关联来源 ID、归并依据 |
| 范围 | AMH/HASE、受影响服务／组件、严重级别及其原始定义 |
| 时间 | 发生、发现、恢复、关闭时间；原始时区；未知值 |
| 影响 | 业务影响描述及有证据的影响量，不能从叙述自行推算损失 |
| 原因 | 触发因素、已确认根因、促成因素、原因标签及审核状态 |
| 应对 | 临时措施、长期修复、关联 Problem/Action、负责人和状态 |
| 证据 | 邮件标识／PPT 页码、原文片段、来源版本、审核人及更新时间 |

## 统计口径

- 从事故清单统计事故数，不能只统计有 RCA 的资料；另报 RCA 覆盖率，定义分子和分母。
- 同时影响 AMH 与 HASE 的事故，在总体中按唯一 ID 计一次；各范围受影响次数不能直接相加为总体。
- 恢复时长与工单关闭时长分开。缺失时间不填零；指标展示有效样本数、缺失数及时间范围。
- 原因可多标签，标签次数之和可能超过事故数。根因未确认时保留未知。
- 版本化分类与计算口径；历史严重级别不可未经确认强制映射。跨年比较注明覆盖及口径变化。
- 重复事故须先定义“重复”的判定规则并经负责人确认；业务量变化时，不把次数变化直接解释为可靠性变化。
- 台账查询或脚本生成数字，LLM 解释时引用计算结果及关联事故；不从检索命中的几份文档估算全量。

## Wiki 结构与运行方式

计划维护四类页面：单次事故、系统／组件、故障模式、HCC 改造主题。统一引用事故 ID 和来源版本，避免从多份二手摘要反复推导事实。

- **Ingest**：识别新增／修订来源，提取并审核，更新相关页面及变更日志。
- **Query**：事实回到来源，数字回到台账计算；回答注明范围和资料截至时间，证据不足时说明未知。
- **Lint**：检查失效引用、孤立页、重复页面、冲突和来源更新。链接及结构可用规则检查，事实与因果仍需领域评审。
- **修订**：源资料修订后标记关联页面待复核，保留旧版本及修订理由；模型建议不直接变成已确认 RCA。

原始来源保持只读；派生页面继承来源的访问限制。混合不同权限材料前必须确认可见范围；源材料撤回或权限变化时复核派生内容。使用哪个 AI 环境及是否存放内部材料，见 D-06。

## HCC 改造证据

使用 [候选项模板](../templates/modernisation-candidate.md) 记录历史事故、问题机制、控制缺口、目标设计变化和验证方式。系统负责人确认事实，HCC 架构负责人评审适用性与优先级。

候选项是建议；不能仅凭旧系统曾发生事故就认定迁移会消除问题。整改状态来自现有工单，保留查询时间，避免另建一套失真的行动清单。
