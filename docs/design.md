## 组织原则

对 INC / RCA，以“一个事故、一组来源、一份可核实的事实记录”为基础。邮件和 PPT 是证据载体，事故是事故知识组织与计数的基本单位；同一事故的邮件链、多版 RCA、PPT 和整改工单关联同一稳定事故 ID。RCA 修订保留版本与修订关系，不新增事故计数；无 RCA 的事故仍保留记录。

事故记录保留历史事实，跨事故页面引用这些记录，迁移适用性判断单独记录在 HCC 候选项中。支持以下追溯关系：

> 事故及 RCA／来源版本 → 故障机制／历史控制 → 目标设计中的对应位置 → 处理决定 → 验证场景与证据

一个事故可关联多个设计问题，一个设计问题也可由多个事故支撑。目标架构尚未确定时，先整理事故事实与来源，迁移关联保留“待评估”。

上游处理由公司内部平台承担：`.msg`、PDF 等原始材料 → 忠实原文、保留来源定位的 Markdown。ITSO 将转换结果上传到本工作台，或提供 TXT／直接粘贴正文；本工作台不自建 `.msg`／PDF 解析库、附件解析或 OCR。主流程为：按 INC 手动补料 → Agent 生成有依据的差异候选 → ITSO 核对原文与变化 → 采纳为新版本 → 更新跨 INC 跟进清单 → 沟通输出 → 补入外部回复继续跟进。报告 Review 完成后，未关闭的 Action 仍在此流程中。

### 记录归属与来源

自有 Web 统一维护持久业务记录，通过获准 API 调用模型。公司内部平台负责原始文件解析及向 Markdown 转换，ITSO 手动转交输出；本工作台接收文本、维护来源关联并生成差异候选，不直接解析原始二进制文件，也不新增自动平台接入要求。邮件、会议记录是外部业务确认的来源，Web 记录采纳与版本；ServiceNow / COSY 继续维护事故处理和措施更新。以上不预设具体数据库、框架或部署方式。

2026-10-31 后续用户确认首版使用已有公司内网环境，项目部署权限及模型 API 调用权限已具备，并已在该环境成功调用；原始邮件、会议纪要、附件与提取后的业务记录均可在该环境保存。这些作为环境设计前提，具体配置、登录与访问、保留及恢复、API 协议与限制仍沿用 D-06 / D-10 待明确；当前会话未独立执行联调，也未开始软件实现或真实资料处理。

| 逻辑记录 | 建议保留的信息与边界 |
|---|---|

| 结论、分歧与确认 | 结论版本、支持及相反证据、具体确认人／角色／时间和确认对象；会议讨论、模型推断与明确确认区分 |
| 差异与采纳记录 | 当前值、候选值、原文依据、受影响对象及基准版本；ITSO 的采纳／暂缓、时间和生成的新版本；历史不覆盖 |

本工作台的补料入口仅接收 **Markdown、TXT 和直接粘贴的正文**。`.msg`、PDF 及其附件等原始材料的解析全部在公司内部平台完成；本工作台不承担扫描件、图片或图示的识别能力建设。覆盖简体中文、繁体中文、英文及混合文本；接收文本的数量、大小和编码由代表样本核实。文本读取失败或平台只转换出部分内容时展示缺口，保留原补料和上次有效记录，不据此断言“没有相关信息”。

#### 内部平台解析输出与来源要求

平台输出是可核对的原文转换结果，必须忠实原文，不能改写、概括、翻译或用摘要替代正文。只允许不改变内容含义的格式转换；保留数字、否定、限定语、表格行列对应关系、发言人／时间和新发言／历史引用边界。无法提取的页面、附件或内容明确标记，不能补写或静默省略。内部平台的实际转换质量仍需样本核对，平台已有能力不等于该输出已符合要求。

| 来源信息 | 必须保留的内容及用途 |
|---|---|
| 原始身份 | 原文件名；涉及附件时同时保留父邮件／文件与附件名。上传后的 Markdown 文件名不能替代原文件名；一份输出合并多份来源时逐段标明对应原文件 |
| 原文位置 | 原 PDF 页码及段落、原邮件／文本段落等可回查位置，并把转换文本片段对应回该位置；不能仅引用转换后 Markdown 的行号来冒充原文定位 |
| 来源与输出版本 | 原文件版本和本次转换输出版本分别保留；重新转换或原文修订须可区分，不覆盖旧输入和历史引用；缺失版本标记待补，不由模型补造 |
| 转换覆盖与原文回查 | 标明已转换范围、缺页／缺段／附件遗漏或识别不确定处；保留获准环境中的原材料回查方式，供 ITSO 对照。原文件留在公司获准来源，不要求上传到本工作台 |

TXT 和粘贴正文同样保留来源、段落和版本；来自文件时填写原文件名，无文件载体的邮件正文保留原邮件标识／标题，不虚构文件名。缺少来源定位／版本，或输出只有概括、无法对照原文时，标为“来源待补／无法追溯”，保留待处理提示；不得把它当作可追溯原文证据支持确认，需补齐依据或由内部平台重新转换。工作台核对文本及来源字段，不通过自建解析器尝试补救上游问题。

工作台后续生成的差异说明、摘要和沟通草稿是派生内容，须引用上述来源片段；这与上游转换必须忠实原文的要求分别管理。邮件旧引用仍可回查，但重复内容不能产生新确认或 Action。

### 采纳、修订与关闭

- 原材料和模型输出进入整理区，业务记录先产生差异候选。ITSO 核对的是提取准确性；RCA 依据 SME 确认、Action 依据对应 Owner 确认，缺少明确确认依据的内容不能因 ITSO 点击采纳而升级为“已确认”。正式报告仍由相关负责人 Review。用户已确认可接受本人明确回复的邮件或经本人确认过的会议纪要；仅在纪要中署名不等于本人确认。
- 建议差异绑定被比较的版本，显示新旧内容及原文位置；核对期间底稿变化时重新比较，避免旧差异覆盖新记录。ITSO 可以保留未解分歧或待补项，不被迫选择一个根因。RCA 意见冲突由预先指定的主责 SME 作最终判断，保留其他意见与判断依据；不要求所有 SME 必须一致，也不由 ITSO 裁定。
- 同一材料重复补入、旧邮件晚到或回复中引用旧结论，不直接覆盖当前有效版本；新证据影响原确认时提示受影响内容，按差异核对后采纳，历史确认及被替代关系保留。疑似撤回或冲突即使尚未采纳，也应向 ITSO 显示待核对提示。
- 本地采纳只更新 Web 中的有效业务记录，不写回源工单。模型调用失败、补料文本读取失败、上游转换缺失或采纳未完成时保留上次有效记录及处理状态，不以空结果清除既有结论和待办。
- 报告 Review、Action 被接受、实施完成、验证结果及事项关闭分别记录。报告已审不移除未关闭 Action；一项回复也不自动解决该 INC 的所有分歧。用户已确认：Owner 报告实施后，由对应 SME 或指定业务验证人确认有效性；实施证据和有效性确认齐备后，由指定负责人批准关闭，ITSO 记录依据。关闭后出现可能无效的新证据，先标记待复核，再由原指定负责人决定是否重开，保留历史关闭记录。具体人选、各类验证证据标准及重开判断依据仍待 D-02 / D-07 细化，Agent 不自行宣告有效性、关闭或重开。

RCA 尚未确认时，草稿须如实保留待确认问题、负责人和跟进日期，由 Reviewer 按具体事故决定能否进入正式 Review。报告已 Review 后，新材料若改变 RCA、影响范围或已审 Action 方案，先标记受影响内容，再由 Reviewer 决定是否重审及范围；ITSO 记录决定依据。旧报告内容和原 Review 历史保留，新增材料不自动获得原 Review 的确认。

### 首页、催办与输出

首页以跨 INC 的待跟进事项为单位，展示等谁、等什么、阻塞什么、材料截至时间及建议联系时间；可回到相应 INC、Action 和来源。用户已确认以下首版排序规则，建议由规则计算顺序，模型解释依据并起草消息：

- 取尚未完成的报告提交／Review 节点中最近的日期，按日期先后排序；不设固定临近窗口，直接显示具体日期，已到日期提示核对进展，不推断实际未回复或逾期。
- 没有活动报告日期的事项，包括报告已审后的 Action，排在有活动日期的事项之后；Action 期限单独显示，不替代报告日期参与首层排序。
- 日期层次相同再看是否阻塞整份报告，随后看等待时间；无活动日期的事项也按阻塞、等待排序。Agent 提出阻塞理由，由 ITSO 核对确定。
- 等待从当前未答问题首次已记录的请求算起；部分回复只解除已答问题，再次催办不重置原等待，实际最后联系时间另记。缺少请求时间保留未知。
- ITSO 人工调整显示理由，保留至该跟进项解决或 ITSO 取消；不能以人工置顶改写期限、业务状态或实际联系记录。

来源日期的时区、完全并列的稳定显示次序等技术细节在设计时落实，不能补造未知日期或新增 SLA。

报告／Review 日期、对方承诺的回复期限、Action 计划期限、Agent 建议联系时间分别展示。未提供日期保持未知；没有新材料只能说明“尚未录入回复”，不能判定实际未回复。ITSO 核对后决定实际联系、发送和升级；草稿生成不自动更新最后联系时间。已采纳的反馈更新相应等待项，报告结束后仍保留 Action 的执行／验证跟进。

输出可复制的邮件进展摘要、待确认问题、Action 和催办草稿，以及供现有模板复用的结构化内容。内容引用当前已采纳版本，分歧与未确认信息明确标记；修订后提示旧草稿可能过时，历史输出保留原依据。首版不自动发送、升级、提交或归档；用户已确认首版不必生成固定格式报告文件，由 ITSO 将可复制内容填入现有模板，不把取得模板或开发 Word／PPT 导出作为首版必需条件。

## MVP1：历史批量整理与新事故同步

以下保留整体 MVP1 的设计建议，自动同步、历史批量导入和 Wiki 发布不是首个 ITSO 切片的前置依赖。用户确认事故处理仍在 ServiceNow / COSY 中，本平台同步记录、协助复盘和出报告；接口、字段映射、同步频率与正式 INC 模板尚未确认。整体范围以 README 为准。

### 历史资料批量整理

1. 按年份和系统建立获准来源清单，提取邮件、PPT 及已有 INC / RCA，记录读取范围、缺失与冲突；尽可能对账权威事故目录。本次建议纳入相关历史 FF log 作为补证，独立计数，不把普通支持记录转成事故。
2. Agent 辅助关联同一事故及资料版本，形成结构化候选与 Wiki 预览；整理人核对提取和身份，SME 核对因果及专业判断。缺少原事故 ID 时生成内部候选 ID 并保留待匹配状态，不自行编造源工单号；身份未核实的候选不计入正式事故总数。
3. 按约定格式导出。建议将事故主记录、整改措施、来源关联分表，以稳定 ID 连接，并携带版本与审核清单；CSV 作为可选交换格式。版本化事实与引用作为 MI 和正式 Wiki 的共同依据，数据库承载台账查询及计算。字段、枚举、时间与时区及空值规则需先确认。
4. 导入前展示新增、更新、重复及错误／待核对记录；保留批次、来源版本与校验结果。重复导入同一来源版本不增加事故数，跨批次修订保留更新依据，关联不明的记录不自动覆盖已确认事实。
5. 核对导入结果及覆盖范围后供 MI 使用；异常单独保留待处理。历史整理与后续同步遇到同一源工单时关联既有事故，不另计一次。

### 新事故同步、复盘与 INC 报告

建议从源系统创建事故记录后开始同步；此前尚未落入源系统的电话或告警，能否被平台获取仍待确认。同步是产品要求，不表示已经具备实时接口。

| 阶段 | 原处理系统 | 本平台建议行为 |
|---|---|---|
| 事故建立 | 创建工单，登记现象、影响、级别及负责人 | 建立同一事故的关联视图，显示来源和同步时间；缺失保留未知 |
| 持续处理 | 更新调查、操作、交接、结果与处理状态 | 累积可获取的事件及证据，整理时间线与信息缺口，供 MI 查看已知情况 |
| 业务恢复 | 记录恢复结果、时间及业务验证 | 引用恢复事实和验证证据，区分恢复、工单关闭及根因确认 |
| 复盘 | 在原流程中确认事实、RCA 及整改工单 | 协助补证与整理复盘，关联源 RCA／措施；推断继续标为待确认 |
| INC 报告 | 沿用既有审核责任，具体模板与归档位置待确认 | 基于指定来源快照生成草稿，人工核对并留存修订；导出／归档方式待定 |

INC 草稿可在处理中形成，未知部分不补造；报告复核状态与源工单处理状态分开。定稿应记录报告版本、资料截至时间及复核人；新证据或 RCA 修订触发受影响报告待复核，保留旧版本，不静默改写已审报告。

### 数据权威与同步边界

- **处理事实的来源**：事故状态、处理负责人、执行动作及整改工单状态引用 ServiceNow / COSY。两系统各自负责哪些字段、跨系统 ID 如何对应、冲突交由谁确认，仍待 D-02 / D-10 盘点，不采用“最后收到的值必然正确”。
- **平台维护的内容**：来源索引、整理摘要、复盘补充、缺口和报告版本／复核进度。补充注明提供人、时间及依据；对源字段的纠错先回原流程确认，平台不把本地编辑当作源状态变更。
- **时间与可见性**：区分事件发生时间、源记录更新时间和平台同步时间。显示最近成功同步、覆盖范围及失败／延迟；保留最后已知快照并标记，不能把缺数据当作零事故或已关闭。若接口只能提供当前快照，不补造缺失的历史事件。
- **接入建议**：优先评估单向读取／导入；API、事件通知、定时同步或受控导出由现有能力决定。当前范围未包含工单派单、生产执行或自动写回；报告最终提交和归档方式待确认。
- **统计一致性**：同一事故的历史资料、新同步记录、FF log、RCA 及 INC 报告共用关联 ID；报告修订不增加事故数。MI 区分处理中事故、已恢复事故和根因未确认事故；缺失恢复时间的事故不计作零时长，恢复指标仅基于有完整依据的样本。

HTML 保留内置来源与响应、CSV 下载、本页模拟台账及版本化 INC 草稿，并已按三个 MVP1 入口重组：MI 下钻同一事故的复盘、证据与报告；资料与质量集中历史批次、同步状态和差异核对。另有两条 FF log 来源索引示例，分别展示关联事故与身份待核对，不增加事故数。字段级局部发布和自动抽检尚未实现；原型未接入真实平台或模型。接口可行性沿用 D-10、权限环境沿用 D-06，新增流程验收沿用 D-05 / D-10；原 P-01 至 P-06 不自动覆盖持续同步与报告流程。

| 整改与验证 | 外部措施 ID、事故关联、负责人、期限、源状态及查询时间；验证结论、环境和证据单列 |
| INC 报告 | 报告 ID 与不可变版本，绑定事实／来源快照、模板版本、截至时间、缺口和审核记录 |
| Wiki / 知识项 | 稳定 ID、引用的事故／结论版本、生成及复核记录；跨事故主题和 SOP 各自记录适用性 |

这些是逻辑对象，不预设建表数量。MVP1 先实现必要的事故、证据、复核、措施与报告契约；MVP2 再展开通用知识发布。CSV 不能只传一份无版本扁平表；至少能从接收记录追到来源、确认范围和一次发布。

### 独立状态与复核责任

- **源处理状态**：引用原系统的处理中／恢复／关闭等状态，不由本平台改写。
- **整理状态**：已接入 → 已提取 → 待核对／可发布 → 已发布；失败和冲突独立排队。源结构化事实满足规则时可直接进入可发布，不必经历模型推断。
- **结论状态**：候选、待确认、已确认、受修订影响、被替代／撤回。源记录的“已确认”只有在确认身份和规则可验证时才继承；模型自评分不能替代审核。
- **报告状态**：草稿、待审、已审版本、需新版本。修订保留原审核及输入，不静默撤销历史审核事实；新版本需重新按报告规则复核。
- **整改状态**：源工单状态与有效性验证分别维护，完成与验证有效不互相替代。

档案可以同时“业务已恢复／根因待确认／报告草稿／整改进行中”。仅已确认根因进入正式根因分组，事故本身仍可计数；字段冲突不必阻塞无争议字段，身份冲突则暂停该候选的正式计数。导出和下钻均携带这些区别。

源事实映射由数据负责人确认；文档提取按经验证的规则、关键字段核对及抽检方案处理；新增原因与机制关联交 SME；INC 走约定报告审批，已存在的源审核尽可能复用。复核画面显示原值／新值、原文定位、变化原因和影响的数字／报告；按业务影响及等待情况排队，不给每条日志新增一个审批任务。具体自动发布阈值和角色沿用 D-02 / D-07 待定。

### 发布、修订与异常恢复

| 情况 | 建议行为 |
|---|---|
| 重复文件／批次／事件 | 依据源身份与版本去重，返回新增／更新／跳过／隔离回执；允许重试，不依赖文件名判断同一内容 |
| 同一事故跨历史与新增路径出现 | 复用身份映射；无可靠映射则保留候选，由人工确认后合并；保留别名、原关联和合并记录，误合并可纠正 |
| 旧版本晚到或来源冲突 | 不按接收先后覆盖，按来源版本及已约定字段权威处理；不可比版本进入冲突队列 |
| 一批资料部分失败 | 失败项隔离；仅发布满足关联完整性的记录单元，缺少必要来源或父对象的记录不得发布；回执暴露未发布范围 |
| 已采纳根因被修订 | 新候选不覆盖原确认；显示存在新证据。确认后切换当前分析版本，重算受影响指标、标记相关 Wiki／报告需复核，保留旧快照 |
| 来源明确撤回原结论 | 将原结论从当前已确认分析中排除并提示撤回；保留历史审计，不能继续把它当作当前有效结论 |
| 同步失败／仅取得当前状态 | 保留最后成功快照及新鲜度提示，不补造历史事件，不以缺失覆盖旧值 |
| 来源权限变化／撤回资料 | 限制相应原文和派生视图访问，按保留政策处理快照与导出；不可因历史报告存在而绕开当前权限 |

发布记录建议包含发布 ID、契约／分类版本、对象版本、来源与确认范围、数据截至时间、更新或撤回意图及接收回执。首次校验应先运行代表性小批次并核对实际输出，再扩大处理；规则／模型变更不自动重新发布全部历史结果。上述为设计条件，尚未实现交易、重放或审计机制。

MI 查询在一个一致的数据版本与权限范围内计算；保存视图／导出时记录过滤条件、口径版本和快照。总数与明细权限须一致，受限来源也不能通过聚合数字、摘要或下载泄露；可共享摘要需独立的可见范围依据。历史报告用于复现当时认知，当前 MI 用于反映当前采纳的记录，两者允许因修订不同，但必须解释差异。

### 代码、运行与资料的边界

建议先在现有 repo 内分离接入处理、领域规则／契约、查询报告与 UI；历史 worker 和增量任务可独立运行。单个代码仓库便于同一变更同步更新契约和消费方，代价是需要明确模块责任。两个 repo 适合独立代码权限、团队和发布周期，代价是契约兼容、跨仓修订和排障协调。当前尚无证据证明后者的收益超过成本。

原始资料、候选、事实记录及报告存放于各自获准位置，不因采用一个代码仓库而混放。本轮用户同意代码仓库与知识内容仓库分工，Wiki 及知识版本独立维护；内容更新不要求重新发布 Dashboard。保留 LLM Wiki 的 ingest / query / lint 思路，但修改 Wiki 中的事实须形成变更候选并回到统一发布流程，不能让 Wiki 和数据库各自成为事实主版本。知识仓库名称、获准环境、访问与发布机制，以及未来应用代码拆分与部署最终依 D-06 / D-10 确认，第二个仓库尚未创建。

## MVP2：日常 FF log 与 SOP

本节指日常知识贡献、检索和 SOP 生命周期；v0.3 建议把历史 FF log 的事故补证与关联放入 MVP1，尚待确认。按 D-09 的讨论方向扩展日常支持知识，保留现有“响应告警／消息／电话 → 处理 → 写 FF log → 发给值班同事”流程。告警、处理日志、问题与事故是不同对象；多条日志可关联同一问题，普通处理记录无需转成 INC 或 SOP。

- **复用日志**：使用 [FF log 模板](../templates/ff-log.md) 建立原记录索引。FFer 提供原记录位置即可开始整理；原文已有内容由整理人引用／提取，只针对影响理解或复用的缺口请记录者补充，不要求重写报告或填满所有字段。
- **保留依据**：沿用原 ID、位置、版本、记录者和访问范围。重发／转发不作为新问题；修订保留关系。补充与纠错注明提供人、日期和依据，处理成功不等于根因已确认。
- **形成 SOP**：整理人／Owner 先检索已有 SOP，基于可核实记录提出修订或使用 [SOP 模板](../templates/sop.md) 起草；保留来源，明确适用条件、步骤、结果检查、停止与恢复路径。普通日志可仅归档或关联已有知识。
- **复核与维护**：SOP 区分草稿、待验证／复核、已审核、待复核和已退役。验证与审核绑定 SOP、系统及环境版本，建议由另一位领域人员复核；旧日志中的一次成功不能直接成为通用操作依据。具体角色与发布规则仍待 D-07 / D-09 确认。
- **减少反馈负担**：使用结果继续写在原 FF log／工单，只增加 SOP ID、版本及实际偏差；SOP 页引用该反馈。实时处理状态留在既有工单中，迁移设计判断留在候选项中。

两个模板均为讨论稿，不代表已经建立导入或发布机制。日志格式和存储／发送渠道尚待确认，资料处理与存放需满足 D-06；日常日志与 SOP 的扩展试点尚未制定或执行。

## MVP2：现场排障助手：报错日志 → 历史 case → 补救建议

面向所有 FFer 增加问题处理中的使用入口：将本次完整报错日志或受控来源交给 agent，由 agent 基于可访问的 repo 知识快速定位历史 FF case、INC / RCA 和 SOP，提出本次优先采用的补救方案。此处的输入是系统产生的现场报错日志；FF log 是处理后编写并共享的处理记录，二者不能混为一类。

建议流程：

1. **理解现场**：从日志提取时间线、错误特征、组件及已发生的结果，定位到文件与行／事件位置。尽量复用现有告警和上下文，仅补问影响方案选择的信息，例如系统版本、当前业务影响、近期变更和已尝试操作。说明已读取的文件及时间范围，日志过长、缺段或未读完时不能声称已分析全部。
2. **检索与比较**：返回相关 case 和 SOP 的 ID、位置、版本与状态，说明相似点、关键差异和适用条件。相同错误码或症状只是线索，不等于根因相同；已退役或影响正确性而待复核的 SOP 不作为操作依据。
3. **形成建议**：先给出当前证据下的首选建议及理由，再列必要备选与切换条件。综合适用性、证据、业务影响、可恢复性和已有授权约束，不用检索相似度或未经校准的置信分数代替判断。“最佳”指当前已知条件下最合适的建议，不承诺唯一最优或必然恢复。
4. **按结果收敛**：建议先做能区分候选原因的只读检查；有适用依据和必要前提时，再列补救步骤。每步带预期结果、观察方法、停止条件和失败后的回退／升级路径。关键条件缺失、来源冲突或没有适用 case 时，明确暂不能给出可靠补救方案，提供最少必要检查与升级方向，不拼凑生产命令或参数。
5. **复用处理日志回流**：FFer 仍按既有流程决定并执行操作。实际采取的步骤、未采用建议、结果及偏差写入原 FF log／工单，必要时引用 agent 建议记录与知识版本，不另填报告。领域复核后再决定是否修订 case 或 SOP；agent 的回答不自动成为已确认知识。

建议回答结构：

| 内容 | 应说明什么 |
|---|---|
| 当前判断与首选建议 | 已观察事实、原因假设、推荐动作及尚未满足的条件分别标明 |
| 历史依据与差异 | case / SOP ID、位置、版本、状态，与本次环境或现象的匹配及不匹配点 |
| 先做的检查 | 检查什么、预期看到什么、结果如何影响下一步选择 |
| 补救步骤与验证 | 操作适用条件、预期结果、业务恢复判据；不能只检查告警消失 |
| 失败处理与备选 | 何时停止、如何恢复／回退或升级，以及改用备选的条件 |
| 未知项与覆盖范围 | 缺失信息、未读取日志、未确认结论及实际检索的知识版本／时间 |

这是建议生成能力的设计，不是自动修复授权。完整日志只可在 D-06 获准的环境与范围内处理，按要求处理敏感字段；临时分析不等于允许把日志或答案写入 repo。所有 FFer 可参与不扩大来源权限。日志和检索文本均作为待核实的数据，不得把其中夹带的指令当作 agent 操作授权。

后续扩展试点应覆盖已知 case、相似症状但原因不同、无匹配 case、SOP 过期、日志缺失和补救失败等情境，检查引用准确性、适用性判断、是否识别未知及停止条件；暂未执行，也不以历史检索命中视为补救有效。具体输入入口、接入工具、日志处理范围与验收条件仍待 D-06 / D-09 及扩展试点确认。

## 邮件与 PPT 的资料处理

本节保留历史资料整理范围；首个切片的 `.msg`、PDF 等原始材料解析由内部平台承担，工作台仅接收转换后的 Markdown、TXT 及粘贴正文。以下历史整理建议不构成工作台自建解析库或 OCR 的要求。

1. 建立来源清单：分配 `source_id`，记录原始位置、资料类型、时间、版本、访问范围及内容指纹（可用时）。具体存储平台待定。
2. 邮件保留主题、时间、邮件链和附件关系；识别转发、引用正文及重复附件，防止重复计算。
3. PPT 检查正文、表格、图片中的文字、图表标注和备注。保存幻灯片序号；图表与 OCR 结果须与原页核对，不能把提取成功当成内容完整。
4. 优先通过原始 incident ID 关联；没有 ID 时，仅依据日期、系统、影响及描述提出关联候选，由人工确认。相似症状不等于同一事故或同一根因。
5. 同一事故可关联多份资料。区分事故发生时间、文档创建时间和修订时间；较晚邮件不自动覆盖已批准 RCA，冲突保留并交由负责人确认。
6. 确认后生成台账及 Wiki 页面。无法读取、定位或确认的内容进入缺失清单，保留处理状态。

## 台账建议字段

| 分组 | 字段 |
|---|---|
| 身份 | 内部唯一 ID、原系统 ID、关联来源 ID、归并依据 |
| 范围 | AMH/HASE、受影响服务／组件、严重级别及其原始定义 |
| 业务场景 | 业务流程、处理阶段、业务时间窗口 |
| 时间 | 发生、发现、恢复、关闭时间；原始时区；未知值 |
| 影响 | 业务影响描述及有证据的影响量，不能从叙述自行推算损失 |
| 原因 | 触发因素、已确认根因、促成因素、故障传播过程、原因标签及审核状态 |
| 历史依赖 | 当时相关组件、接口、数据状态、处理顺序及平台行为；仅记录有证据的内容 |
| 应对 | 临时恢复、长期修复、监控与预防控制、关联 Problem/Action、负责人和状态 |
| 有效性 | 整改是否验证有效、验证条件及证据；与工单关闭状态分开记录 |
| 证据 | 邮件标识／PPT 页码、原文片段、来源版本、审核人及更新时间 |

使用 [事故模板](../templates/incident.md) 保留业务场景和从触发、发现、影响扩散到恢复的时间线。每项关键事实附来源位置与版本；缺失不补齐，推断和冲突单列。工单关闭不能代替整改有效性证据。

## 统计口径

- 从事故清单统计事故数，不能只统计有 RCA 的资料；另报 RCA 覆盖率，定义分子和分母。
- 同时影响 AMH 与 HASE 的事故，在总体中按唯一 ID 计一次；各范围受影响次数不能直接相加为总体。
- 恢复时长与工单关闭时长分开。缺失时间不填零；指标展示有效样本数、缺失数及时间范围。
- 原因可多标签，标签次数之和可能超过事故数。根因未确认时保留未知。
- 版本化分类与计算口径；历史严重级别不可未经确认强制映射。跨年比较注明覆盖及口径变化。
- 重复事故须先定义“重复”的判定规则并经负责人确认；业务量变化时，不把次数变化直接解释为可靠性变化。
- 台账查询或脚本生成数字，LLM 解释时引用计算结果及关联事故；不从检索命中的几份文档估算全量。

## Wiki 结构与运行方式

INC / RCA 部分计划维护四类页面：单次事故、系统／组件、故障模式、HCC 改造主题；日常支持扩展增加 FF log 索引与 SOP，问题经验优先关联既有问题记录。各类页面引用对应稳定 ID 和来源版本，避免从多份二手摘要反复推导事实。

| 浏览入口 | 组织内容 |
|---|---|
| 业务流程视角 | 引用相关事故、业务阶段及迁移验证场景 |
| 系统／组件页面 | 引用涉及的事故、历史依赖及控制措施 |
| 故障模式页面 | 记录机制描述、适用条件、关联事故、归组依据及确认状态 |
| HCC 改造主题页面 | 汇总候选项及其关联的设计决定、验证场景和证据 |

这些入口引用同一份事故事实，不分别维护副本。年份、AMH/HASE、严重级别作为筛选维度，用于趋势分析。

故障模式的关联须记录支持及相反证据、来源版本和审核人。症状相似不代表机制相同；尚未确认的关联保留为候选，不计入已确认重复问题。重复统计口径仍待 D-04 确认。

- **Ingest**：识别新增／修订来源，提取并审核，更新相关页面及变更日志。
- **Query**：事实回到来源，数字回到台账计算；回答注明范围和资料截至时间，证据不足时说明未知。
- **Lint**：检查失效引用、孤立页、重复页面、冲突和来源更新。链接及结构可用规则检查，事实与因果仍需领域评审。
- **修订**：源资料修订后标记关联页面、SOP、迁移判断及验证场景待复核，保留旧版本及修订理由；目标设计或验证输入变化时重新评估原结论与证据的适用性。模型建议不直接变成已确认 RCA 或已审核 SOP。

原始来源保持只读；派生页面继承来源的访问限制。混合不同权限材料前必须确认可见范围；源材料撤回或权限变化时复核派生内容。使用哪个 AI 环境及是否存放内部材料，见 D-06。

## HCC 改造证据

使用 [候选项模板](../templates/modernisation-candidate.md) 记录历史事故、问题机制、控制缺口、目标设计变化和验证方式。系统负责人确认事实，HCC 架构负责人评审适用性与优先级。

历史 RCA 描述事故发生时的情况；迁移适用性判断引用 RCA，并绑定目标设计版本，不能写回为原 RCA 的结论。每项候选记录回答：

- 原故障条件在目标设计中是否仍存在？依据是什么？
- 原有控制由什么机制承接，需要保留、替换还是重新验证？
- 若认为不再适用，具体是哪项设计变化消除了发生条件？
- 尚缺哪些信息、由谁确认？未决项保留待评估状态。

候选项是建议；不能仅凭旧系统曾发生事故就认定迁移会消除问题。整改状态来自现有工单，保留查询时间，避免另建一套失真的行动清单。

## 迁移验证场景

在候选项模板中按场景逐项记录，使用稳定场景 ID，关联事故及 RCA／来源版本。每个场景包含业务前置条件、触发或故障注入方式、预期业务结果、观察方法及验收条件；由业务与架构负责人确认适用性和验收条件，不凭历史资料自行设定缺失阈值。

场景设计与执行结果分开。后续执行证据须记录环境、目标系统／构建及设计版本、实际结果、证据位置、执行时间和审核人。未执行保持“未执行”，设计已评审不等于验证通过；旧平台的整改验证也不能代替新平台的验证。

本节仅定义未来记录方式，不启动场景执行、故障注入或真实资料处理。
