01

FFer 的一天，怎么用？

点击场景查看建议流程。以下均为通用使用情境，不是已发生的内部事件。

新增场景 · 现场排障助手 · 待设计

给出现场日志，得到有依据的补救建议。

FFer 在获准环境提供本次完整报错日志或受控来源。agent 基于 repo 中的 FF case、INC / RCA 和 SOP，说明“建议先做什么、为什么适用、如何确认有效”。

① 理解本次问题

定位报错、时间线与组件；复用告警上下文，只补问影响方案选择的信息。日志缺段或未读完时明确说明覆盖范围。

② 快速查历史 case

列出相关 case / SOP、版本与状态，解释相似点和关键差异。相同错误码不直接等于相同根因。

③ 给出首选与备选

在当前证据下，按适用条件、业务影响和可恢复性推荐方案，说明备选切换条件；不承诺唯一最优或必然恢复。

④ 先检查，再补救

先做能区分原因的只读检查，再给出有适用依据的补救步骤、预期结果和业务恢复判据。

⑤ 无依据或操作失败

没有适用 case、关键条件缺失时，明确暂不能可靠推荐；提供必要检查。补救步骤须说明停止、回退／恢复及升级路径。

⑥ 结果回到 FF log

FFer 按既有授权决定并执行操作；实际动作、结果和偏差仍写原日志／工单，关联建议及知识版本，不另写报告。

两种日志：输入是现场系统报错日志，处理后输出的是 FF log。当前页面只讨论能力，不接收日志、不自动修复；完整日志的处理环境和权限待 D-06 确认，临时分析不等于自动入库。

建议回答顺序：当前判断与首选建议 → 历史依据及差异 → 必要检查 → 补救与验证 → 失败处理／备选 → 未知项。详见 设计细节。

场景 A · 接班 / 开始一天的工作

从未完成事项进入，看到相关知识。

查看本班相关服务、交接记录和未闭合问题，再进入适用的检查清单或 SOP。

查什么

上班遗留项、已知问题、近期变更关联及已审核 SOP 的适用范围。

做什么

核对现有工单中的实时状态，按已有值班流程检查；知识库给出背景和操作依据。

留下什么

补充观察结果、后续动作、负责人及交接链接；注明记录时间。

什么时候需要贡献

检查步骤缺失、信息过时，或发现其他同事需要知道的新情况。

现有工单／值班平台继续作为实时任务状态来源；知识库保存经验和关联，不再维护一套独立的值班队列。

场景 B · 告警 / 业务咨询 / 异常排查

找到相似问题，确认是否适用。

从业务流程、症状、错误特征和组件找到相关问题、事故与 SOP；相似症状仅作为排查线索。

查什么

适用版本、前置条件、已知故障模式、诊断步骤及升级联系角色。

做什么

先检查条件是否匹配，再遵循现有操作权限和支持流程；不确定时升级处理。

留下什么

观察到的事实、已尝试步骤、结果、无效尝试及证据位置。

如何形成知识

新现象建立问题记录；已有方法的差异作为 SOP 修订建议；符合现有事故标准时关联 INC。

不能把历史 RCA 直接当作本次根因。待确认假设与已确认事实分开保存。

场景 C · 处理日志 / 后续整理

同事已收到日志，经验还需要可检索、可复用。

FF log 是值班人员响应生产 alert、消息或电话后编写，并发给所有值班同事的处理日志。这条现有共享流程继续保留；建议从获准的日志来源整理知识，减少重复录入。

建议提取字段

原记录 ID、时间与时区、业务／系统、告警或来电现象、处理动作、结果、后续事项、来源位置及版本；实际字段待核对。

关联与去重

区分告警、处理日志、问题和 INC。保留来源 ID；识别重发／转发和重复导入，人工确认多次告警是否涉及同一问题。

人工确认

导入后核对条数、字段、来源定位、遗漏、重复与冲突。处理成功不等于根因已确认。

分流结果

普通日志可归档；可复用经验进入问题记录；事故链接 INC；可操作方法提出 SOP 草稿。

导入为待设计能力。本页不接收文件。日志格式、保存与发送渠道尚待确认；真实日志只有在处理环境、目标存储及权限获准后才可处理，先核对代表性样本再扩量。

场景 D · INC / RCA

保留一份事故事实，沉淀多种后续用途。

紧急处置遵循现有事故流程；恢复后归并邮件、PPT、日志与工单，维护事故时间线和 RCA 版本。

复盘内容

业务影响、触发因素、根因、促成因素、故障传播过程及当时依赖。

来源规则

同一事故稳定 ID，多份来源共同引用；冲突保留，权威版本由领域负责人确认。

沉淀输出

相关故障模式、诊断或恢复 SOP 候选、整改工单及迁移设计问题。

跟踪结果

工单关闭与整改有效性分开；RCA 修订时检查关联 SOP、设计判断和验证场景。

没有 RCA 的事故也保留。FF log 条数、独立问题数与事故数是不同指标，不能直接互相替代。

场景 E · 重复任务 / 学习与演练

让另一个 FFer 也能正确使用。

按任务找到经过复核的 SOP，确认系统版本、适用条件、操作权限和停止条件后再使用。

读之前

检查状态、负责人、最近验证时间；区分草稿、已审核、待复核和已退役。

操作时

按步骤核对预期结果；结果不符时停止或升级，遵循原有授权及变更要求。

反馈时

关联 SOP 版本，记录适用环境、实际结果、偏差和修订建议。

复用价值

用于日常支持、新人学习及获准环境内的演练，减少重复摸索。

一次处理成功只提供候选经验。SOP 发布前需明确适用边界并由具备领域能力的人员复核验证；不保证因此完全避免复发。

场景 F · HCC modernisation / 设计评审

从历史机制得到设计问题与验证场景。

系统核心从 IBM iSeries 迁移至开放平台时，按业务流程、依赖和故障模式查询历史经验。

提取设计输入

哪些业务约束仍然存在？旧平台承担了什么控制？哪些日常操作暴露出可改进点？

记录设计判断

把历史事实独立关联目标设计版本，说明控制如何保留、替换或重新验证。

提出验证场景

明确前置条件、触发方式、预期业务效果及观察方法，由业务与架构负责人确认。

回流支持知识

新平台验证完成后更新适用的 SOP 和系统说明，保留旧版本及退役关系。

日常日志可以提出设计线索；升级为设计依据前需核实证据。更换平台不自动说明故障机制已消除。

从工作问题进入

“这个症状以前出现过吗？”“这个任务该怎么做？”“这个系统有哪些已知风险？”

共同字段：业务／系统、标签、稳定 ID、来源、确认状态、owner、更新时间及适用版本。年份与 AMH/HASE 用于筛选，不要求只靠目录定位。

真实资料存放边界

Repo 保存什么，需要单独确认

当前 GitHub 仓库继续保存讨论材料、空白模板和虚构演示。未来原始日志与敏感派生知识，应放在获准环境；索引、摘要和 SOP 本身也要检查访问范围。

“所有 FFer 可参与”不等于所有人能看所有来源。派生知识沿用相应权限；仓库私有和 .gitignore 都不是资料上传许可。

怎么贡献，才能进入日常工作？

先让同事容易留下事实，再由明确的负责人把可复用内容整理成知识。以下入口与角色是建议，尚未配置。

入口 A · 所有 FFer

现有处理日志，就是贡献起点

继续处理问题、写 FF log 并发给值班同事。后续整理从获准来源提取事实、处理结果与证据，再请记录者补充缺失信息。

不要求再写一份完整 Wiki 或先学习 Git。纠错可通过获准的现有反馈渠道提交，由维护者代建变更并保留贡献者和来源；具体渠道待确认。

入口 B · 熟悉 Git 的贡献者

提出可复核的变更

先检索既有记录 → 更新既有页面或建立草稿 → 提交 PR → 领域复核 → 维护者合并。

PR 说明改变了什么、依据和适用范围、影响哪些关联内容。当前仓库只允许本任务授权的讨论材料；真实知识贡献入口待 D-06 确认。

已有讨论稿空白模板：FF log 记录模板用于引用原日志、仅补缺口；SOP / Runbook 模板由整理人／Owner 提炼并安排复核。使用结果继续记录在原 FF log／工单，关联 SOP ID 与版本即可，无需重复填写报告。

  1. 1 / Capture提交与定位

    保留来源、作者、时间与版本；资料缺失也可以记录，明确标为待核实。

  2. 2 / Curate筛选与关联

    核对重复、归属和权限，关联已有问题；普通记录可归档，无需全部升格。

  3. 3 / Review领域复核

    核对事实及操作边界。SOP 需有验证依据；AI 草稿不能自行变成已审核内容。

  4. 4 / Reuse发布与反馈

    维护者合并获准内容，保留变更记录；使用反馈链接到具体版本，持续修订。

LLM 的建议职责：辅助提取、分类、关联、起草、检查失效链接，并结合现场日志与历史知识提出有依据的补救建议。统计按固定口径计算；根因、SOP 的有效性和设计决定由相应负责人确认，建议不自动变成生产操作或已审核知识。
04

谁来维护，什么情况下必须更新？

用明确的 owner 和变化触发复核，避免“收集很多、没人敢用”。

责任角色主要工作建议触发时机
FFer / 贡献者记录事实与处理结果，反馈错误或不适用步骤日常处理后、交接时或使用知识发现偏差时
轮值整理人处理新增记录、识别重复、分配领域 owner、追踪待核实项交接时整理新增项；按实际工作量安排定期整理
领域负责人 / SOP owner确认事实、维护适用范围、安排验证、标记过时或退役内容出现新证据、实际使用失败、系统或依赖发生变化时
Repo 维护者维护结构、ID、模板及链接，检查复核记录并合并获准变更每次变更；定期检查无 owner、失效引用及长期待复核内容
架构 / 业务 / 验证负责人评估迁移适用性，确认验收条件，维护设计与执行证据设计评审、版本变更、验证执行及切换准备时

可兼任角色，但操作性 SOP 建议由另一位具备领域能力的人员复核；具体人选、投入、复核周期和合并权限待 D-07 / D-09 确认。

SOP 的建议状态

草稿→待验证 / 复核→已审核 · 限适用范围

来源变化、系统版本变化或使用结果不符时，转为待复核。不再适用的内容标记已退役，保留历史链接与替代方案。

待复核且影响操作正确性的 SOP 应暂停作为操作依据，按既有支持流程升级。发布知识不改变生产操作所需的授权。

复用前必须说清楚

一个 SOP 应包含什么？

  • 目的、适用系统／版本、前置条件及所需权限
  • 每步操作、预期结果、观察方法和停止条件
  • 失败时的回退／恢复方式；无法回退时的升级路径
  • 来源、owner、复核人、验证环境及证据
  • 最近验证时间、复核触发条件、版本与替代关系
05

经验怎样进入新系统的设计之初？

既看严重事故，也看日常支持反复出现的困难；形成证据后进入设计和验证。

① 日常与事故证据

关联 FF log、问题、RCA 和 SOP，保留业务场景、机制及历史控制。

② 设计问题

哪些条件会保留？哪些手工步骤可改进？原有控制如何由新平台承接？

③ 设计决定

绑定目标设计版本，记录保留、替换或不适用的判断及确认人。

④ 验证与回流

定义预期业务效果；后续记录实际执行证据，并更新新平台支持知识。

纯假设示例：如果多份支持记录显示某任务经常需要人工恢复，先核实原因与条件，再讨论是否改进恢复机制；验证关注故障后的业务一致性和可恢复性。不能仅凭“记录很多”认定架构有缺陷。
怎么判断这个知识库是否有用？

建议观察：同事能否找到适用知识、SOP 实际使用的成功与偏差反馈、知识校正和维护耗时、重复支持工作是否减少，以及设计评审是否引用了可核实的历史证据。先约定口径和基线，不设未经讨论的目标数字，也不以页面数量代替价值。

为什么不能把 FF log 数量直接作为事故趋势？

多条记录可能属于一个问题，一个问题也可能不是事故。日常工作量、问题频次和唯一事故数应分别统计，并注明采集覆盖范围；只有 RCA 确认并符合既定规则的关联才进入已确认重复事故统计。
